# Watch telemetry: capture and limits

Spottr currently requests heart-rate access and records a traditional indoor strength workout. The live contract contains heart rate in bpm, wrist user-acceleration magnitude in g, and wrist rotation-rate magnitude in rad/s, each with its measurement timestamp. Missing readings stay absent. HealthKit permission completion does not establish that a readable heart-rate sample exists.

Motion updates are requested every 0.1 seconds, but the current adapter forwards at most one instantaneous pair of magnitudes per second. Those values are not one-second averages, raw vectors, joint angles, lifting force, or validated rep counts. The phone supplies the workout/session identity. The Watch retains the latest readings between messages; downstream report projection deduplicates measurement timestamps and excludes stale readings. This is a latest-value stream, not a lossless archive of every Watch sensor observation.

## Callback lifecycle correction

The previous recorder allowed a delayed failure from an old HealthKit session to end the current workout. An old builder's heart-rate callback could also publish into a later recording, and queued motion callbacks checked only that some workout existed.

`WatchCaptureLifecycle` now owns a run token, collection state, pause state, and motion-stream token. The recorder checks the originating HealthKit session or builder inside the main-actor callback. Ending or replacing a run rejects its samples; pausing rejects heart and motion delivery. Resume creates a new motion stream and resets its throttle, so queued pre-pause motion cannot become its first new sample. Heart and motion readings must also have been measured since capture started or resumed; a cached reading cannot become fresh just because its callback arrived later, even on a new stream. Authorization finishing during a pause starts collection paused rather than publishing movement. Collection and save status callbacks also check run ownership so an older run cannot overwrite the latest run's status.

Seven Foundation-only tests passed after observed compile RED for the missing contract and measurement-time boundaries, plus an observed behavior RED where a new motion stream accepted a cached pre-resume measurement. They cover old-session failure protection, paused/ended/replaced sample rejection, status ownership, fresh motion on resume, delayed pre-pause heart and motion readings, and permission completion while paused. The Watch adapter has a passing source parse. Native Watch compilation and physical-Watch callback/HealthKit acceptance are still separate checks; simulator execution cannot establish live heart-rate capture.

For a physical fixture, start recording A, queue a heart/motion callback, end A, start B, then deliver A's callbacks/failure: B must remain running and receive neither reading nor status from A. Pause B with a queued motion callback, resume, and deliver that old callback before a fresh sample: only the fresh stream may publish. Finish B while its save callback is pending, start C, then complete B's save: C's status must remain current. These schedules can be reproduced with injected callback fakes before relying on timing on a device.

Separate follow-up: `beginCollection(false)` currently reports a collection failure without fully clearing/discarding that current session and builder. A cleanup change needs a callback fake proving it discards only the matching failed collection, stops motion, clears recording state, and leaves a newer recording untouched. This patch does not change that failure path.

## Useful additions, not implemented

| Signal | Meaningful next step | Availability limit |
| --- | --- | --- |
| Active energy | Read current workout energy statistics with units and measurement interval; keep cumulative totals distinct from increments. | Request the appropriate HealthKit access and inspect the data source's actual collected types. Apple lists energy among possible live types; available types depend on settings and configuration. |
| Richer wrist motion | Preserve bounded vector/gravity/orientation windows or report sample-counted RMS/peak motion features. | `CMDeviceMotion` exposes these measurements, but the current wire format discards them. Wrist orientation is not a whole-body posture or joint-angle measurement. Higher-frequency batching needs runtime support checks and a storage/battery budget. |
| Observed rest HR trend | Compare actual pre/post-rest windows with sample counts, timestamps, and gaps. | Only report a change when fresh samples exist; do not present it as the HealthKit one-minute recovery metric or a readiness diagnosis. |
| HRV, resting HR, sleep, respiratory rate | Query authorized historical samples and show when and from which source they were measured. | Apple documents respiratory rate during sleep and automatically recorded HRV. Some newer models offer daytime HRV, but none of this establishes a continuous live strength-workout stream on this user's Watch. Empty results stay unavailable. |
| HealthKit one-minute HR recovery | Show an existing authorized HealthKit sample with its date/source when present. | The type represents post-exercise recovery; its presence for each strength workout must be verified rather than assumed. |

Apple references: [live types to collect](https://developer.apple.com/documentation/healthkit/hkliveworkoutdatasource/typestocollect), [active energy](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/activeenergyburned), [device motion](https://developer.apple.com/documentation/coremotion/cmdevicemotion), [HRV SDNN](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/heartratevariabilitysdnn), [sleep respiratory rate](https://support.apple.com/en-ie/108906), [overnight/daytime vitals and model differences](https://support.apple.com/en-md/120142), and [HealthKit recovery type](https://developer.apple.com/documentation/healthkit/data-types).
